HugeGraph-Loader Quick Start

Bulk import graph data into HugeGraph with Loader from files, HDFS, relational databases, Kafka, and other HugeGraph graphs.

This guide aligns with the Toolchain master branch (currently based on 1.8, unreleased). Released packages and Docker latest may differ; check your version before using unreleased features.

Quick start: local file import

Walk through a minimal import workflow: import two people and one relationship, then verify the data in Hubble. First install Loader and start HugeGraph Server. The commands below run from the Loader directory, importing into the default graph hugegraph. For an authenticated Server, append --username and --password (or --token).

  1. Create the data files.

    These CSV files have no header row. The mapping in the next step supplies the column names.

    1mkdir -p demo-loader
2cat > demo-loader/people.csv <<'EOF'
3docs-smoke-alice,29
4docs-smoke-bob,31
5EOF
6cat > demo-loader/knows.csv <<'EOF'
7docs-smoke-alice,docs-smoke-bob
8EOF

  2. Create the schema and mapping.

    Dedicated docs_* names keep this example separate from the built-in person data. File paths are relative to the directory where you run Loader.

     1cat > demo-loader/schema.groovy <<'EOF'
 2schema.propertyKey("docs_name").asText().ifNotExist().create()
 3schema.propertyKey("docs_age").asInt().ifNotExist().create()
 4schema.vertexLabel("docs_smoke_person").properties("docs_name", "docs_age")
 5      .primaryKeys("docs_name").ifNotExist().create()
 6schema.edgeLabel("docs_smoke_knows").sourceLabel("docs_smoke_person")
 7      .targetLabel("docs_smoke_person").ifNotExist().create()
 8EOF
 9cat > demo-loader/struct.json <<'EOF'
10{
11  "version": "2.0",
12  "structs": [
13    {
14      "id": "people",
15      "input": {
16        "type": "FILE",
17        "path": "demo-loader/people.csv",
18        "format": "CSV",
19        "header": ["docs_name", "docs_age"]
20      },
21      "vertices": [{"label": "docs_smoke_person"}]
22    },
23    {
24      "id": "knows",
25      "input": {
26        "type": "FILE",
27        "path": "demo-loader/knows.csv",
28        "format": "CSV",
29        "header": ["source_name", "target_name"]
30      },
31      "edges": [{
32        "label": "docs_smoke_knows",
33        "source": ["source_name"],
34        "target": ["target_name"],
35        "field_mapping": {"source_name": "docs_name", "target_name": "docs_name"}
36      }]
37    }
38  ]
39}
40EOF

  3. Run the import.

    Keep the same working directory. Change the host and port if Server runs elsewhere.

    1bin/hugegraph-loader.sh \
2  --graphspace DEFAULT --graph hugegraph \
3  --file demo-loader/struct.json --schema demo-loader/schema.groovy \
4  --host 127.0.0.1 --port 8080

    A first successful run imports two vertices and one edge. Check the success and failure counts in the summary.

  4. Query the result in Hubble.

    Connect Hubble to the same Server and graph, then run these queries separately in the Gremlin workspace.

    1g.V().hasLabel('docs_smoke_person').valueMap('docs_name', 'docs_age')
2g.V().has('docs_smoke_person', 'docs_name', 'docs-smoke-alice')
3 .out('docs_smoke_knows').values('docs_name')

    The first query returns Alice with age 29 and Bob with age 31. The second returns docs-smoke-bob.

For other inputs, continue with the mapping reference. The bundled full example also includes software vertices and edge properties.

1 HugeGraph-Loader Overview

HugeGraph-Loader converts source data into graph vertices and edges and imports them into HugeGraph in batches.

Currently supported data sources include:

  • Local disk file or directory, supports TEXT, CSV and JSON format files, supports compressed files
  • HDFS file or directory supports compressed files
  • Mainstream relational databases, such as MySQL, PostgreSQL, Oracle, SQL Server
  • Kafka topic
  • An existing HugeGraph graph, used to copy data from one graph into another

Local disk files and HDFS files support resumable uploads.

Note: HugeGraph-Loader requires HugeGraph Server service, please refer to HugeGraph-Server Quick Start to download and start Server

Concurrent imports: Loader on the master branch supports LOADING owner protection on the same Server instance when the Server’s GET .../mode/owners returns protocol: 1. Servers without this endpoint retain legacy import behavior without this protection; see the compatibility notes below.

Testing Guide: For running HugeGraph-Loader tests locally, please refer to HugeGraph Toolchain Local Testing Guide

2 Get HugeGraph-Loader

HugeGraph-Loader is available in the following three ways:

  • Use docker image (Convenient for Test/Dev)
  • Download the compiled tarball
  • Clone source code then compile and install

2.1 Use Docker image (Convenient for Test/Dev)

We can deploy the loader service using docker run -itd --name loader hugegraph/loader:latest. For the data that needs to be loaded, it can be copied into the loader container either by mounting -v /path/to/data/file:/loader/file or by using docker cp.

Alternatively, to start the loader using docker-compose, the command is docker-compose up -d. An example of the docker-compose.yml is as follows:

This combination is for local anonymous testing; the Server API is published only on the local host.

 1version: '3'
 2
 3services:
 4  server:
 5    image: hugegraph/hugegraph:latest
 6    container_name: server
 7    ports:
 8      - 127.0.0.1:8080:8080
 9
10  loader:
11    image: hugegraph/loader:latest
12    container_name: loader
13    # mount your own data here
14    # volumes:
15      # - /path/to/data/file:/loader/file

The specific data loading process can be referenced under 4.5 User Docker to load data

Note:

  1. The docker image of hugegraph-loader is a convenience release to start hugegraph-loader quickly, but not official distribution artifacts. You can find more details from ASF Release Distribution Policy.

  2. Pin a published version tag or image digest in production. latest is mutable and does not guarantee alignment with master.

2.2 Download the compiled archive

Choose a published Toolchain archive from the download page and extract it. A release may not include all master functionality; use the source build below for the implementation described here.

2.3 Clone source code to compile and install

Building Loader from the master branch requires Java 17, Maven 3.6.3+, and Python 3.9+. Clone the repository and build:

1git clone --branch master --single-branch https://github.com/apache/hugegraph-toolchain.git
2cd hugegraph-toolchain
3mvn package -pl hugegraph-client,hugegraph-loader -am -DskipTests -ntp
4cd hugegraph-loader/apache-hugegraph-loader-*

To build against candidate Server SDKs during development, refer to the Java 17 migration guide.

For Oracle input, obtain a JDBC driver JAR compatible with your Oracle/JDK versions and place it in the extracted Loader lib/ directory. The startup script loads JARs there; installing a driver only in the local Maven repository does not put it on Loader’s runtime classpath.

3 How to use

To import a dataset, prepare the schema, data and mapping, then run Loader.

  • Write graph schema
  • Prepare data files
  • Write input source map files
  • Execute command import

3.1 Construct graph schema

Define the vertex labels, edge labels and properties needed to represent your data before writing the schema.

The example below uses person and software vertices, connected by knows and created edges. People have names, ages and cities; software has a name and price. Each edge records a date.

graph model example

Save the schema definitions in schema.groovy.

 1// Create some properties
 2schema.propertyKey("name").asText().ifNotExist().create();
 3schema.propertyKey("age").asInt().ifNotExist().create();
 4schema.propertyKey("city").asText().ifNotExist().create();
 5schema.propertyKey("date").asText().ifNotExist().create();
 6schema.propertyKey("price").asDouble().ifNotExist().create();
 7
 8// Create the person vertex type, which has three attributes: name, age, city, and the primary key is name
 9schema.vertexLabel("person").properties("name", "age", "city").primaryKeys("name").ifNotExist().create();
10// Create a software vertex type, which has two properties: name, price, the primary key is name
11schema.vertexLabel("software").properties("name", "price").primaryKeys("name").ifNotExist().create();
12
13// Create the knows edge type, which goes from person to person
14schema.edgeLabel("knows").sourceLabel("person").targetLabel("person").properties("date").ifNotExist().create();
15// Create the created edge type, which points from person to software
16schema.edgeLabel("created").sourceLabel("person").targetLabel("software").ifNotExist().create();

See HugeGraph Client for the schema API.

3.2 Prepare data

The data sources currently supported by HugeGraph-Loader include:

  • local disk file or directory
  • HDFS file or directory
  • Partial relational database
  • Kafka topic
  • An existing HugeGraph graph
3.2.1 Data source structure
3.2.1.1 Local disk file or directory

Set the input path to a local file or a directory. A single input source accepts one directory, not a list of directories.

For data split across part-0, part-1 and other files, place those files in one directory and set the mapping’s path to that directory.

Supported file formats include:

  • TEXT
  • CSV
  • JSON

TEXT uses a configurable delimiter. Each data row represents a record; its columns supply IDs, labels or properties. Column names can come from a header row or from the mapping’s header setting.

An example is as follows:

1id|name|lang|price|ISBN
21|lop|java|328|ISBN978-7-107-18618-5
32|ripple|java|199|ISBN978-7-100-13678-5

CSV is a TEXT file with commas , as delimiters. When a column value itself contains a comma, the column value needs to be enclosed in double quotes, for example:

1marko,29,Beijing
2"li,nary",26,"Wu,han"

The JSON file requires that each line is a JSON string, and the format of each line needs to be consistent.

1{"source_name": "marko", "target_name": "vadas", "date": "20160110", "weight": 0.5}
2{"source_name": "marko", "target_name": "josh", "date": "20130220", "weight": 1.0}
3.2.1.2 HDFS file or directory

Users can also specify HDFS files or directories as data sources, all of the above requirements for local disk files or directories apply here. In addition, since HDFS usually stores compressed files, loader also provides support for compressed files, and local disk file or directory also supports compressed files.

Currently supported compressed file types include: GZIP, BZ2, XZ, LZMA, SNAPPY_RAW, SNAPPY_FRAMED, Z, DEFLATE, LZ4_BLOCK, LZ4_FRAMED, ORC, and PARQUET.

3.2.1.3 Mainstream relational database

The loader also supports some relational databases as data sources, and currently supports MySQL, PostgreSQL, Oracle, and SQL Server.

Loader does not follow foreign keys to query other tables while parsing a row. Each input row must provide the values needed to construct its graph elements. Prepare any joins in the source query first.

Consider three tables named person, software and created.

1// person schema
2id | name | age | city
1// software schema
2id | name | lang | price
1// created schema
2id | p_id | s_id | date

If person and software use PRIMARY_KEY IDs with name as the primary key, each edge needs its endpoints’ names. The created table contains only p_id and s_id; Loader will not query the names from those IDs. Use either of these ID designs.

  1. Keep PRIMARY_KEY and use each vertex table’s id column as its primary key property. Loader can then build endpoint IDs from p_id, s_id and the vertex labels.
  2. Use custom IDs, taking each vertex table’s id column as the vertex ID. The edge mapping can use p_id and s_id directly.

Both designs let edge rows supply endpoint IDs without another lookup.

3.2.2 Prepare vertex and edge data
3.2.2.1 Vertex Data

The vertex data file consists of data line by line. Generally, each line is used as a vertex, and each column is used as a vertex attribute. The following description uses CSV format as an example.

  • person vertex data (the data itself does not contain a header)
1Tom,48,Beijing
2Jerry,36,Shanghai
  • software vertex data (the data itself contains the header)
1name,price
2Photoshop,999
3Office,388
3.2.2.2 Edge data

The edge data file consists of data line by line. Generally, each line is used as an edge. Some columns are used as the IDs of the source and target vertices, and other columns are used as edge attributes. The following uses JSON format as an example.

  • knows edge data
1{"source_name": "Tom", "target_name": "Jerry", "date": "2008-12-12"}
  • created edge data
1{"source_name": "Tom", "target_name": "Photoshop"}
2{"source_name": "Tom", "target_name": "Office"}
3{"source_name": "Jerry", "target_name": "Office"}

The 1.0 version of the mapping file is centered on the vertex and edge, and sets the input source; while the 2.0 version is centered on the input source, and sets the vertex and edge mapping. Some input sources (such as a file) can generate both vertices and edges. If you write in the 1.0 format, you need to write an input block in each of the vertex and edge mapping blocks. The two input blocks are exactly the same; and the 2.0 version only needs to write input once. Therefore, compared with version 1.0, version 2.0 can save some repetitive writing of input.

In the bin directory of hugegraph-loader-{version}, there is a script tool mapping-convert.sh that can directly convert the mapping file of version 1.0 to version 2.0. The usage is as follows:

1bin/mapping-convert.sh struct.json

A struct-v2.json will be generated in the same directory as struct.json.

The bin directory also ships utf8-bom-to-utf8.sh, which strips the UTF-8 BOM from a single data file, or from every file under a directory. It is useful when a CSV or TEXT file exported by a Windows tool fails to parse because its first header column carries an invisible BOM:

1bin/utf8-bom-to-utf8.sh /path/to/file-or-dir
3.3.2 Input Source

Input sources are currently divided into five categories: FILE, HDFS, JDBC, KAFKA and GRAPH, which are distinguished by the type node. We call them local file input sources, HDFS input sources, JDBC input sources, KAFKA input sources and GRAPH input source, which are described below.

3.3.2.1 Local file input source
  • id: The id of the input source. This field is used to support some internal functions. It is not required (it will be automatically generated if it is not filled in). It is strongly recommended to write it, which is very helpful for debugging;
  • skip: whether to skip the input source, because the JSON file cannot add comments, if you do not want to import an input source during a certain import, but do not want to delete the configuration of the input source, you can set it to true to skip it, the default is false, not required;
  • input: input source map block, composite structure
    • type: an input source type, file or FILE must be filled;
    • path: the path of the local file or directory, an absolute path or a path relative to the Loader process working directory (not the mapping file). An absolute path is recommended; required;
    • file_filter: filter files with compound conditions from path, compound structure, currently only supports configuration extensions, represented by child node extensions, the default is “*”, which means to keep all files;
    • format: the format of the local file, the optional values are CSV, TEXT and JSON, which must be uppercase, the default is CSV, optional;
    • header: column names; if omitted, the first data line supplies them. With an explicit header, an identical first line is still skipped by default (see has_header). JSON does not require a header; optional;
    • has_header: for CSV and TEXT, the first line of every file is dropped when it is identical to the header, so a header repeated in each part file of a directory is not imported as data. Set this to false to turn that check off when the first line of a file is real data that happens to equal the header, optional;
    • delimiter: The column delimiter of the file line. The default depends on format: a comma "," for CSV and a tab "\t" for TEXT; a CSV file accepts no other delimiter. The JSON file does not need to be specified, optional;
    • charset: the encoded character set of the file, the default is UTF-8, optional;
    • date_format: custom date format, the default value is yyyy-MM-dd HH:mm:ss, optional; if the date is presented in the form of a timestamp, this item must be written as timestamp (fixed writing);
    • extra_date_formats: a list of fallback date formats, tried when a value does not match date_format, empty by default, optional;
    • time_zone: Set which time zone the date data is in, the default value is GMT+8, optional;
    • skipped_line: The line to be skipped, compound structure, currently only the regular expression of the line to be skipped can be configured, described by the child node regex. The default regex is (^#|^//).*|, which skips lines starting with # or // and empty lines; to keep such lines, set regex to a pattern that matches nothing, optional;
    • compression: The compression format of the file, the optional values ​​are NONE, GZIP, BZ2, XZ, LZMA, SNAPPY_RAW, SNAPPY_FRAMED, Z, DEFLATE, LZ4_BLOCK, LZ4_FRAMED, ORC and PARQUET, the default is NONE, which means a non-compressed file, optional; for ORC and PARQUET the header is matched case-insensitively;
    • list_format: When a column of the file (non-JSON) is a collection structure (the Cardinality of the PropertyKey in the corresponding figure is Set or List), you can use this item to set the start character, separator, and end character of the column, compound structure :
      • start_symbol: The start character of the collection structure column (the default value is the empty string "", JSON format currently does not support specification)
      • elem_delimiter: the delimiter of the collection structure column (the default value is |, and it must differ from delimiter; JSON format currently only supports native , delimiter)
      • end_symbol: the end character of the collection structure column (the default value is the empty string "", the JSON format does not currently support specification)
      • ignored_elems: the elements dropped after the column is split, the default value is [""], so empty elements are ignored

3.4.2 Breakpoint Continuation Mode

For a long import, use a progress file to resume after an interruption.

Set --incremental-mode to true to resume from a progress file. Loader records progress when it closes normally after a successful import or a normal stop; an unexpected failure may prevent this write. The progress file is in ${struct} and named load-progress_${timestamp}, where ${struct} is the mapping-file prefix and ${timestamp} is the import start time, formatted as yyyyMMdd-HHmmss. For example, an import started at 2019-10-10 12:30:30 with mapping file struct-example.json writes struct-example/load-progress_20191010-123030. When the directory holds several progress files, the resumed import reads the last one in name order, which is the most recent one.

Note: A progress file is written after a successful import or a normal stop (including an error limit), regardless of --incremental-mode or --print-progress. An import aborted by an unexpected failure may not write one.

After stopping an import with Ctrl+C or kill, set --incremental-mode true to continue from the recorded position. A forced stop with kill -9 cannot save progress.

Invalid data or connection failures can exhaust --max-read-errors, --max-parse-errors or --max-insert-errors. Correct the rows in the failure files, then use --failure-mode true to retry them. This leaves the original data files unchanged. Rows that still fail are recorded again and deduplicated when the failure file closes. Failure mode lifts these three limits and scans the entire file.

Each input source, that is each item of structs in the mapping file, gets its own failure file. The file is named after the id of that input source with the suffix .error and is stored in the ${struct}/failure-data directory. Every failed line is written as a pair of lines: a tip line starting with #### READ ERROR:, #### PARSE ERROR: or #### INSERT ERROR:, followed by the original data line. When the input source has a header, that header is written as JSON to a sibling ${id}.header file, so the failure file can be read back with the right columns. For example, if the mapping file has an input source with id 1 holding a vertex mapping person and an input source with id 3 holding an edge mapping knows, each of which has some error lines, you will see the following files in the ${struct}/failure-data directory when the Loader exits:

  • 1.error: the failed lines of input source 1, each preceded by its tip line
  • 1.header: the header of input source 1, written only when that input source has a header
  • 3.error: the failed lines of input source 3
  • 3.header: the header of input source 3

A .error file that turns out to be empty is deleted when the Loader exits, so only the input sources that really had failed lines leave a file behind. In incremental mode new failures are appended to the existing file, otherwise the file is rewritten from scratch.

3.4.6 Concurrent imports and LOADING ownership

In the master branch, Loader implements a LOADING ownership protocol coordinated with Server’s /mode/owners endpoint. When the deployed Server provides this endpoint and returns protocol: 1, Loader enables ownership protection automatically; released Server 1.7.0 and older versions continue using the legacy mode switching flow.

  1. Probe and Acquire: Loader probes /mode/owners. The first Loader obtains an ownership handle (instance/epoch/token), transitioning graph mode from NONE to LOADING; concurrent Loaders can join.
  2. Data Import: Loaders holding valid handles execute concurrent imports while preserving LOADING mode.
  3. Graceful Release: When an import completes, Loader drains its workers and releases its handle. When the last owner releases, graph mode automatically returns to NONE.
  4. Failure Recovery: If abnormal exit (e.g. kill -9) leaves an orphaned owner, stop and drain all related imports and graph writes, then perform administrator recovery via the RESTful API recovery endpoint or restart the Server. Manual release applies only when the caller still holds its token (e.g. a direct REST client).
Note

Compatibility and Operational Notes

  • Legacy Compatibility: During ordinary imports, only an unsupported-route 404 status on /mode/owners falls back to the legacy enum LOADING/NONE flow (maintains compatibility with Server 1.7, without multi-loader protection). Network or permission errors, or a 404 for a missing graph, do not trigger fallback.
  • Restore and Graph Source Imports: Retain the RESTORING flow without ownership probes or automatic resets. After a restore import completes, manually reset graph mode to NONE before starting ordinary imports. Do not run restore, graph-source, Spark connector, or older Loader imports while owned imports are active.
  • Scope & Lifecycle: Ownership is bound to the target Server instance without cross-node synchronization or automatic lease expiry. For embedded programmatic integrations, callers must invoke HugeGraphLoader.shutdown() to attempt a single graceful release. If release fails, the handle is not retried; the owner may remain active on the Server, and the administrator recovery step above may be required.

4.5 Use Docker to load data

4.5.1 Use docker exec to load data directly
4.5.1.1 Prepare data

For a first import, use the built-in example dataset.

For custom data, first copy the files into the Loader container.

Prepare the data, schema and mapping as described in sections 4.1 to 4.3, then copy them with docker cp.

The following example stores the files in hugegraph-dataset.

1tree -f hugegraph-dataset/
2
3hugegraph-dataset
4├── hugegraph-dataset/edge_created.json
5├── hugegraph-dataset/edge_knows.json
6├── hugegraph-dataset/schema.groovy
7├── hugegraph-dataset/struct.json
8├── hugegraph-dataset/vertex_person.csv
9└── hugegraph-dataset/vertex_software.txt

Copy the files into the container.

1docker cp hugegraph-dataset loader:/loader/dataset
2docker exec -it loader ls /loader/dataset
3
4edge_created.json  edge_knows.json  schema.groovy  struct.json  vertex_person.csv  vertex_software.txt
4.5.1.2 Data loading

Run this command to import the built-in dataset.

For custom data, set -f to your mapping file and -s to your schema file.

You can refer to 3.4.1-Parameter description for the rest of the parameters.

1docker exec -it loader bin/hugegraph-loader.sh -g hugegraph -f example/file/struct.json -s example/file/schema.groovy -h server -p 8080

If loading a custom dataset, following the previous example, you would use:

1docker exec -it loader bin/hugegraph-loader.sh -g hugegraph -f /loader/dataset/struct.json -s /loader/dataset/schema.groovy -h server -p 8080

Also update every input.path in the custom struct.json to its actual container path, such as /loader/dataset/vertex_person.csv. Changing only -f and -s does not change where Loader looks for data files.

If loader and server are in the same Docker network, you can specify -h {server_container_name}; otherwise, you need to specify the IP of the server host (in our example, server_container_name is server).

4.6 Import data by spark-loader

The current master API sink uses Spark 3.5.8, Scala 2.12 and Java 17 on the driver and executors. The POM’s Spark 3.2.2 dependency supplies compile-time APIs; it is not the runtime engine. Set SPARK_HOME and JAVA_HOME, then use the distribution’s shaded Loader JAR with its launcher.

Create the schema first and make data files readable by the executors. CSV and TEXT inputs need headerless UTF-8 data and an explicit mapping header. Other charsets and has_header: true are rejected. Load vertex data before edge data when the edges depend on those vertices. Replace the mapping path below with your prepared vertex mapping.

1bin/hugegraph-spark-loader.sh \
2  --master 'local[2]' --driver-memory 1g \
3  --file /path/to/vertex-mapping.json \
4  --host 127.0.0.1 --port 8080 --graph hugegraph --sink-type true

Pass Spark options such as --master, --conf and --jars to the launcher alongside Loader options. Additional JDBC drivers need explicit --jars; copying them into lib/ does not distribute them to executors. Query the target graph to verify counts and properties; the API sink’s insertion counters do not report distributed writes.

This path rejects --incremental-mode true and --failure-mode true. Standalone Spark supports client deployment only. HBase bulkload (--sink-type false) is unsupported on Spark 3.5.8 / Java 17; keep an existing bulkload deployment on its separately validated released Loader/JVM/Spark/HBase environment. For details, see the Spark migration guide.

4.7 Import data by flink-cdc-loader

The current master integration targets Flink 2.2.1, MySQL CDC 3.6.0-2.2 and Java 17. Older examples using Flink 1.13.5 and CDC 2.2.1 belong to the previous implementation. Set FLINK_HOME; the submission JVM, JobManager and TaskManager must all use Java 17. Keep Flink’s module-access options and exactly one shaded Loader JAR in the distribution’s lib/.

Each mapping needs a MySQL JDBC input with url, database, table, username and password. Set MySQL binlog_row_image=FULL. UPDATE events require explicit, nonempty update_strategies and unchanged graph IDs; changes to vertex IDs, edge endpoints or sort keys are rejected. CDC also rejects --dry-run true and --use-prefilter true.

Without a separator, all arguments go to Loader. To set Flink options, put them before -- and Loader options after it. For a prepared mapping at mysql-cdc.json, submit with one sink writer.

1bin/hugegraph-flinkcdc-loader.sh -p 1 -- \
2  --file ./mysql-cdc.json --host 127.0.0.1 --port 8080 \
3  --graph hugegraph --cdc-sink-parallelism 1

Each mapping uses a single source reader and sink writer. --cdc-sink-parallelism defaults to 1; other values are rejected. After --, Loader’s -p means the Server port. Checkpoint flushing does not provide transactional graph writes or an exactly-once guarantee. Validate edge CDC and broader mappings in your test environment before deploying to production. For more details, see the Flink CDC documentation.

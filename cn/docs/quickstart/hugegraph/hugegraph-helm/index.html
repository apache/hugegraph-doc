使用 Helm 部署 HugeGraph

本文适用于 HugeGraph 1.8.0 及以后版本，需要支持 OCI 的 Helm 3.10+ 和 Kubernetes (K8s) 1.23+。 可从 GHCR 或 Docker Hub 安装 hugegraph-helm。Chart 与 HugeGraph 服务分别维护版本，例如 0.2.x 的 Chart 可以部署 1.8.x 的服务。

警告

当前开发 Chart 使用 latest 镜像，适合测试。 对应 HugeGraph 服务正式发布后，生产环境请选择稳定 Chart，并检查其中的镜像版本。 镜像标签可能变化；需要固定镜像内容时，请配置各组件的 image.digest。

Artifact Hub 方便查找 Chart、查看版本和安装说明，实际安装包仍从 GHCR 或 Docker Hub 下载。 参数和源码开发方式见 chart README， 生命周期操作见 运维参考。

1 安装

说明

默认部署规格与存储要求

  • 拓扑组成：默认部署 3 PD + 3 Store + 3 Server 与 1 Hubble，默认开启鉴权与持久化存储。
  • 存储依赖：需要集群具备默认动态 StorageClass 或预先匹配的静态 local PV，共需 7 个持久卷（3 个 10 GiB PD 卷、3 个 50 GiB Store 卷、1 个 1 GiB Hubble 卷）。
  • 内存考量：保留镜像内 JVM 内存自动推导；按需调整 resource requests/limits，确保宿主机给 9 个图服务 JVM 与 Hubble 提供足够内存。

选择一个下载源即可，公共 CI 推荐 GHCR。本地轻量测试可直接使用单节点预设。

提示

--devel 按版本号选择最新 Chart，包含开发版和稳定版，不限于某个版本系列。 生产部署或需要复现时，将 --devel 换成 --version <已发布版本>，固定你选定的版本。

GHCR（推荐）
1CHART=oci://ghcr.io/hugegraph/hugegraph-helm
2kubectl config current-context
3kubectl get nodes
4kubectl get storageclass
5helm install hugegraph "$CHART" --devel -n hugegraph \
6  --create-namespace --wait --timeout 15m
Docker Hub
1CHART=oci://registry-1.docker.io/hugegraph/hugegraph-helm
2kubectl config current-context
3kubectl get nodes
4kubectl get storageclass
5helm install hugegraph "$CHART" --devel -n hugegraph \
6  --create-namespace --wait --timeout 15m
单节点试用
1# 适合本地 Minikube/Kind 等轻量测试；直接安装本次下载的 Chart
2CHART=oci://ghcr.io/hugegraph/hugegraph-helm
3helm pull "$CHART" --devel --untar
4helm install hugegraph ./hugegraph-helm -n hugegraph \
5  -f ./hugegraph-helm/values-single.yaml \
6  --create-namespace --wait --timeout 10m

单节点试用预设替代默认安装，将各组件设为 1 副本并放宽调度限制，适合资源受限环境。

2 模式和访问入口

解压后目录为 hugegraph-helm/，源码目录仍为 helm/hugegraph/。

HugeGraph Helm 核心文件与结构

  • hugegraph-helm/
    • Chart.yaml#Chart 元数据与版本定义
    • values.yaml#默认配置（easy 模式：3 PD + 3 Store + 3 Server + 1 Hubble，NodePort 入口）
    • values-single.yaml#单节点预设（本地 Minikube/Kind 测试，1 副本且关闭反亲和与 PDB）
    • values-cluster.yaml#生产集群预设（跨节点反亲和调度，Store 采用 OnDelete 逐个滚动升级）
    • values-strict.yaml#安全加固预设（strict 模式：全部 ClusterIP，强制启用 NetworkPolicy 隔离）
    • values.schema.json#values 配置参数校验规范
    • templates/#Kubernetes 资源编排模板
      • pd-statefulset.yaml#PD 服务有状态副本集（元数据与调度中心）
      • store-statefulset.yaml#Store 存储节点有状态副本集（分布式存储引擎）
      • server-deployment.yaml#Server 引擎无状态 Deployment（注入 serviceId / graphSpace）
      • hubble-deployment.yaml#可视化控制台 Deployment
      • tests/#冒烟验证测试钩子（helm test，支持自定义 testGraphAlias）
    • examples/#7 种生产场景完整示例（含 local PV、GitOps 凭据、Ingress 等）
    • docs/operations.md#生命周期进阶运维与故障恢复手册

默认 mode: easy，Server 和 Hubble 自动分配 NodePort，PD 保持 ClusterIP。可以直接使用 HTTP，无需域名、证书或额外确认参数。 mode: strict 默认将 Server/Hubble 设为 ClusterIP，并开启 NetworkPolicy。两个模式都保留鉴权和持久化。 优先级是组件显式参数高于全局参数，全局参数高于模式默认值，显式 false 也会生效。 全局参数包括 persistence.enabled 和 global.imageRegistry，严格预设为 values-strict.yaml。

入口访问方式前提
NodePorthttp://<可达节点IP>:<分配的NodePort>节点网络可达且防火墙放行，无需额外控制器
ClusterIP集群内虚拟 Service IP/DNS，如 hugegraph-server.hugegraph.svc:8080集群外通过 port-forward 或已有网关访问
LoadBalancer基础设施分配的地址集群有对应负载均衡控制器
Ingress通过控制器路由 HTTP 请求已安装 Ingress 控制器，域名和 TLS 都可选
1kubectl -n hugegraph get svc hugegraph-server hugegraph-hubble
2kubectl get nodes -o wide
3kubectl -n hugegraph get secret hugegraph-admin \
4  -o jsonpath='{.data.password}' | base64 --decode

使用 Hubble 的 NodePort 打开页面，以 admin 和查出的密码登录。 默认 externalTrafficPolicy: Cluster 下，访问的节点不必运行目标 Pod。ClusterIP 是集群内部的虚拟服务地址，不是节点 IP，普通笔记本通常不能直接访问。 也可以运行 kubectl -n hugegraph port-forward svc/hugegraph-hubble 8088:8088，在本机打开 http://127.0.0.1:8088。

三个客户端 Service 都支持 externalTrafficPolicy、loadBalancerClass、loadBalancerIP、loadBalancerSourceRanges、externalIPs 和 allocateLoadBalancerNodePorts，具体行为取决于集群及负载均衡实现。LoadBalancer 专用字段应配合对应类型使用。 NodePort 省略或设为 0 时自动分配，固定端口由 Kubernetes 根据集群配置的范围校验，chart 不再强制 30000–32767。 原 HTTP 暴露确认参数保留兼容，但不再阻止渲染。

服务身份与图空间

默认 server.serviceId 与 server.graphSpace 均为 DEFAULT。如需将 Server 注册到指定的业务服务名或图空间，可通过 values 指定：

仅修改已有部署的配置时，保留当前 Chart 版本和 values。用 helm list 查看版本，替换下面的版本占位符：

1helm list -n hugegraph
2CHART=oci://ghcr.io/hugegraph/hugegraph-helm
3CHART_VERSION='<已安装的Chart版本>'
4helm upgrade hugegraph "$CHART" --version "$CHART_VERSION" -n hugegraph --reuse-values \
5  --set-string server.serviceId=analytics \
6  --set-string server.graphSpace=team_a \
7  --set-string server.testGraphAlias=team_a-demo

注意：非默认图空间必须在启动 Server 前先调用 PD API 创建；server.testGraphAlias 用于指定 helm test 验证的 Gremlin 图别名（区分大小写）， 不会从 graphSpace 自动推导。请勿在 server.extraEnv 中重复声明服务 ID 或图空间。

3 内网镜像和存储

完整例子包含内网镜像、动态存储、七个 local PV、 GitOps 凭据、仅 API 部署以及无域名的 HTTP Ingress。

global.imageRegistry 为未指定 registry 的镜像仓库加前缀，组件指定完整 registry 地址时优先采用组件配置。 默认只需镜像仓库中的 hugegraph/pd、hugegraph/store、hugegraph/server 和 hugegraph/hubble 四个镜像，标签或 digest 按实际配置选取。 等待 PD 的 init container 复用 Store 镜像，Helm test 复用 Server 镜像。这两个镜像已包含 curl，无需额外 curl 镜像或启动时安装软件。 自定义镜像可以继续使用显式 store.waitImage 和 server.waitImage 覆盖。

存储配置

storageClassName 为空时继承集群默认 StorageClass，"-" 表示显式不使用 StorageClass。 local PV 需要预建宿主机目录、匹配容量、nodeAffinity 和 kubernetes.io/no-provisioner StorageClass。 WaitForFirstConsumer 根据 Pod 调度约束绑定，创建资源前请查看七个卷的完整例子。 新建临时实例可以设置 persistence.enabled=false 使用 emptyDir，组件存储开关优先。 PVC 失败不会自动降级为临时存储，已经初始化的 PD/Store 切换存储模式会被拒绝。

离线安装和私库

先选择最新版本，再按该版本下载 Chart，将 .tgz 搬入内网。可以直接安装，也可以接入已有的 OCI 或 HTTP 私库。 内网安装需通过 --set global.imageRegistry=... 覆盖镜像私库， 参见 values-internal-registry.yaml。

1CHART=oci://ghcr.io/hugegraph/hugegraph-helm
2CHART_VERSION=$(helm show chart "$CHART" --devel | sed -n 's/^version: //p')
3helm pull "$CHART" --version "$CHART_VERSION"
直接安装
1# 内网环境需覆盖镜像私库（或使用 -f values-internal-registry.yaml）
2helm install hugegraph "./hugegraph-helm-${CHART_VERSION}.tgz" -n hugegraph \
3  --set global.imageRegistry=registry.example.com \
4  --create-namespace --wait --timeout 15m
OCI 私库
1helm registry login registry.example.com
2helm push "./hugegraph-helm-${CHART_VERSION}.tgz" oci://registry.example.com/charts
3helm install hugegraph oci://registry.example.com/charts/hugegraph-helm \
4  --version "$CHART_VERSION" -n hugegraph \
5  --set global.imageRegistry=registry.example.com \
6  --create-namespace --wait --timeout 15m
HTTP 私库
1# 按私库的上传方式接收同一个 .tgz，并更新 index.yaml。
2# 自建静态 HTTP 源可用 helm repo index 生成索引；helm push 只适用于 OCI。
3helm repo add hugegraph-internal https://charts.example.com
4helm repo update hugegraph-internal
5helm install hugegraph hugegraph-internal/hugegraph-helm \
6  --version "$CHART_VERSION" -n hugegraph \
7  --set global.imageRegistry=registry.example.com \
8  --create-namespace --wait --timeout 15m

私库地址请替换为实际地址。Chart 包不包含容器镜像；完整离线部署还需搬运配置引用的所有容器镜像，并覆盖镜像地址。

4 鉴权和 Secret

普通 Helm 安装自动生成、复用三份凭据，分别为 <release>-admin 的 password、<release>-auth-token 的 token_secret 以及 <release>-pd-auth 的 secret-key。PD REST 使用共享的 PD Secret，通过 HG_PD_AUTH_SECRET_KEY 注入 PD 容器， Server 等待存储和 Hubble 使用同一份凭据，不需要用户为每个 PD Pod 单独发明密码。

GitOps 使用加密的固定值，或预先创建 Secret 并配置 pd.auth.existingSecret、server.auth.admin.existingSecret 和 server.auth.token.existingSecret。existingSecret 高于内联值，chart 不管理这类外部 Secret。 管理员密码需要可打印 ASCII，不能包含空格、冒号、反斜杠；PD 密码需要可打印 ASCII，不能包含首尾空白和反斜杠；JWT key 至少 32 字节。 离线渲染器不能通过 lookup 读取在线已生成 Secret，因此不能依赖每次渲染随机生成凭据。

管理员 Secret 是初始凭据，更新 Secret 不会修改已经创建的账户密码。 先使用旧密码调用 PUT /graphspaces/DEFAULT/auth/users/admin，请求体为 {"user_password":"<新密码>"}， 再把 Secret 和源配置同步为新密码，最后重启 Server Deployment 清理所有副本的鉴权缓存。

Hubble 默认开启，当前镜像的登录仍依赖 Server 鉴权。只使用 API 可以设置 hubble.enabled=false， 如需关闭 API 鉴权，再设置 server.auth.enabled=false。未使用的凭据配置可以留在 values 中。

5 升级和验证

使用 Helm 原生值复用保留已有部署的 UI、入口、存储和凭据设置。

1helm get values hugegraph -n hugegraph --all
2# 测试环境继续跟随最新版本；生产升级请改用 --version 指定已审阅的稳定版本。
3helm upgrade hugegraph "$CHART" --devel -n hugegraph \
4  --reuse-values --wait --timeout 15m
5helm test hugegraph -n hugegraph --logs --timeout 5m

已有配置中的显式 helper 镜像也会保留。添加 --set-string store.waitImage= --set-string server.waitImage= 可清空覆盖并复用组件镜像。 要采用新的默认值，先审阅已有配置，再使用 --reset-values 和保留镜像、凭据、存储、拓扑设置的配置文件。 PD 成员、持久存储和共享凭据变更需要按生命周期说明协调处理。

基于当前 master 构建的 PD、Store 和 Server 镜像以 UID/GID 10001 运行。除非 podSecurityContext 已设置 fsGroup，Chart 会为 PD 和 Store Pod 设置 fsGroup: 10001（以及 fsGroupChangePolicy: OnRootMismatch），即使 --reuse-values 保留了旧 Release 的空值也是如此，使其能写入旧镜像（以 root 运行）创建的 PVC。

请在首次应用 fsGroup 的同一次滚动更新中，将 PD 和 Store 切换到基于此版本构建的镜像，使 kubelet 在 10001 镜像启动前修改卷的属主。不要先用仍以 root 运行的镜像（例如尚未更新到此版本的 latest）运行此 Chart：这些镜像创建的文件归 root 所有，而 OnRootMismatch 只检查卷的根目录，之后不会再修正它们。 请将 pd.image 和 store.image 固定为基于此版本构建的镜像，而不要依赖 latest。非空的 image.digest 优先于 image.tag，且 --reuse-values 会保留已有的 digest，因此按 digest 固定镜像的 Release 必须修改 digest，而不能只修改标签。

如果 Release 已在设置了 fsGroup 的情况下运行过 root 镜像，请在首次滚动更新到 10001 镜像的同时执行一次递归属主变更。请在同一条命令中设置镜像， 使递归变更作用于 10001 镜像，而不是已固定的 root 镜像。示例清空了保留下来的 digest，使标签生效；按 digest 固定镜像的 Release 应改为将 pd.image.digest 和 store.image.digest 设为此版本镜像的 digest：

1helm upgrade hugegraph "$CHART" --devel -n hugegraph --reuse-values \
2  --set pd.image.tag=<this-version> \
3  --set store.image.tag=<this-version> \
4  --set-string pd.image.digest= \
5  --set-string store.image.digest= \
6  --set pd.podSecurityContext.fsGroupChangePolicy=Always \
7  --set store.podSecurityContext.fsGroupChangePolicy=Always \
8  --wait --timeout 15m

改回原策略前，请确认每个 PD 和 Store Pod 运行的都是你设置的 10001 镜像，而不是旧的 root 镜像：

1kubectl get pods -n hugegraph \
2  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].image}{"\n"}{end}'

--reuse-values 会保留 Always，而它会在每次 Pod 启动时遍历整个卷，因此请在这些 Pod 运行后改回原策略：

1helm upgrade hugegraph "$CHART" --devel -n hugegraph --reuse-values \
2  --set pd.podSecurityContext.fsGroupChangePolicy=OnRootMismatch \
3  --set store.podSecurityContext.fsGroupChangePolicy=OnRootMismatch \
4  --wait --timeout 15m

CSI 驱动忽略 fsGroup 的卷（例如许多 NFS 驱动）和 hostPath 卷需要改为执行一次 chown -R 10001:10001。

server.storageWaitTimeoutSeconds 默认 300，通过 WAIT_STORAGE_TIMEOUT_S 传给启动脚本。 未指定的启动探针阈值按存储等待加 150 秒推导；显式探针不会被改写，但预算必须覆盖存储等待和至少 120 秒 Server 启动时间。 矛盾预算会在渲染时报出对应参数。这个等待超时不是 JVM 内存配置。

默认 helm test hook 检查连接和读取。安装或恢复后，还应重新登录 UI，并验证应用实际使用的读写查询。 调度、NetworkPolicy、滚动升级和恢复见 Kubernetes 运维。
